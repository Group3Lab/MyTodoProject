# task 与 taskSystem 修改注意事项

本文档说明修改 [task.py](../core/taskModule/task.py) 和 [taskSystem.py](../core/taskModule/taskSystem.py) 时大家共同遵守的约定，避免各改各的、改坏接口或让菜单数据出错。

**这两个文件谁都能改，没有「专属负责人」。** 写这份文档不是划地盘，而是因为这两个文件是所有菜单的公共底座：改动会影响每个人的功能，所以更要提前说清楚怎么改。约定是为了让大家随便改也不会互相踩到，而不是限制谁不能改。

配套阅读：[添加新功能指南](./添加新功能指南.md)（讲怎么加菜单）、[作业需求](./作业需求.md)（讲最终要实现什么）。

## 一、模块职责与分层

| 层 | 文件 | 职责 |
| --- | --- | --- |
| 数据模型 | `core/taskModule/task.py` | 只描述「一条任务」有哪些属性、怎么校验 |
| 数据管理 | `core/taskModule/taskSystem.py` | 保存任务列表，提供增删改查接口 |
| 菜单层 | `menus/*.py` | 只负责交互，通过 `TaskSystem` 的公开方法读写数据 |

三层每个人都可以改；分工只是建议，不是门槛。唯一的要求是**改哪一层就守住那一层的规矩**：

- 改 `task.py`：属性、校验、序列化这三件事归它管。
- 改 `taskSystem.py`：列表的增删改查、索引边界归它管。
- 改 `menus/`：只管交互，不要绕开 `TaskSystem` 直接操作数据。

**核心原则：数据合法性只能由 `Task` / `TaskSystem` 保证；菜单层不允许碰 `Task` 的内部字段。**

## 二、task.py 修改注意事项

1. **有新属性就在 `__init__` 里初始化默认值，并做好封装**
   新增属性一律用 `self.__xxx = 默认值` 的形式定义，并配套 `@property`，保证对象一创建就处于合法状态。
2. **绝对不准改 `__init__` 的参数列表（硬性规定）**
   原注释已经写明「不要动参数列表，有新参数先创建再修改」，这是必须遵守的规矩，不是建议。
   正确流程固定为两步：
   - 第一步：在 `__init__` **函数体里**给新属性创建默认值并封装好，`__init__` 的签名一个字都不动。
   - 第二步：属性就位后，再通过 `TaskSystem` 的专用设置方法按流程设值（写下 setter 校验、写完 `update_xxx` 方法），走正常流程把值设进去。

   ```python
   # 正确：参数列表保持只有 title，新字段在函数体里先创建
   def __init__(self, title):
       if not title or not title.strip():
           raise ValueError("任务标题不能为空")
       self.__title = title.strip()
       self.__priority = "中"          # 新属性：先创建默认值
       self.__due_date = ""            # 新属性：先创建默认值
   ```

   `Task(title)` 这种调用形式在菜单层到处都是，一旦动了参数列表，所有人的调用点会同时失效。**不带默认值的"先创建再修改"就是不走流程、直接破坏接口，不做。**
3. **校验逻辑必须留在构造函数 / setter 里**
   现有标题校验（空、全空白抛 `ValueError`）不能挪到菜单层。菜单层只做输入提示，真正拒绝非法数据的是 `Task`。
4. **setter 必须写防乱写入逻辑**
   参照被注释掉的那段 `is_completed` 写法：
   ```python
   @is_completed.setter
   def is_completed(self, value: bool):
       if not isinstance(value, bool):      # 补充防乱写入逻辑
           raise ValueError("完成状态必须是布尔值")
       self.__is_completed = value
   ```
   恢复注释代码时要补上类型/范围校验，否则外部能写入 `"yes"`、`1` 这类脏数据。
5. **`to_string()` / 解析格式与需求保持一致**
   作业要求一行文本、字段用 `|` 分隔：
   ```
   标题 | 优先级 | 截止日期 | 是否完成
   ```
   注意被注释的旧写法是 `f"{self.title}|{self.is_completed}"`，它输出的是 `True/False`，**不符合需求**，要按需求改成 `高 / 中 / 低`、`YYYY-MM-DD`、`未完成 / 已完成`。存储、显示、解析三处必须用同一种格式，解析时字段数、顺序要严格对应，标题本身不允许包含 `|`。
6. **新增字段的默认值要「可读回」**
   日期统一 `YYYY-MM-DD`（月、日补 0），这样比较先后可以直接比字符串大小；优先级只允许 `高/中/低`，比较时不要直接按字符串排序。

## 三、taskSystem.py 修改注意事项

1. **属性一律用私有 `__tasks` 存放**
   外部只能通过方法操作，不要为了图方便暴露列表或提供返回内部列表的方法。
2. **区分「返回引用」和「返回副本」两个取任务方法**
   - `_get_by_index(idx)`：返回内部引用，**仅供 `TaskSystem` 内部使用**。修改数据必须走专用方法，不要在外部拿它直接改字段。
   - `get_by_index(idx)`：返回 `deepcopy` 副本，**给菜单层只读使用**。
   菜单类里禁止调用 `_get_by_index()`；改成返回引用、或把 `deepcopy` 去掉，都会让菜单能绕过校验直接改数据。
3. **索引边界要用 `0 <= idx <= len(self.__tasks)-1` 这种不越界判断**
   非法索引统一返回 `None` / `False`，不要抛异常。
4. **注意 `deepcopy` 的代价**
   返回副本需要 `from copy import deepcopy`，`Task` 的字段越多越贵。如果以后要频繁遍历（筛选、排序、统计），优先在 `TaskSystem` 内加只读查询方法，不要在菜单里循环调用 `get_by_index()`。
   **（后续会移除深拷贝不用管这条，只是做好数据保护防止乱改）**
5. **新增修改类方法写在「分割线」之后，与属性一一对应**
   每个可改属性配一个专用方法（如 `update_completed(idx, status)`），返回 `bool` 表示是否成功；方法内部先用 `_get_by_index()` 取引用再赋值，不要直接 `self.__tasks[idx].xxx = ...`（否则少了越界判断）。

   这套方法是「先创建再走流程设置」的第二步：`Task.__init__` 里先把属性建好（默认值），这里再提供按流程设值的入口。

   ```python
   def update_priority(self, idx: int, priority: str) -> bool:
       """更新任务的优先级（走流程设置，不直接改字段）"""
       task = self._get_by_index(idx)
       if task:
           task.priority = priority      # 通过 setter 走校验
           return True
       return False
   ```

   对应地，`Task` 那边要同时提供 `priority` 的 `@property` + 带校验的 setter，两边一起改才是一条完整的流程。
6. **不要修改已有的公开方法签名**
   `add(title)`、`get_by_index(idx)`、`delete(idx)`、`get_task_count()` 已被多个菜单使用。要加参数必须给默认值；要改返回值必须同步排查所有调用点。
7. **保持 `add()` 的返回值和职责**
   `add()` 返回新建的 `Task` 对象（菜单靠它打印标题），不要改成返回索引或 `None`。
8. **目前被注释的接口不要擅自放开**
   `update_completed()` 和 `Task.is_completed` 是留给「标记完成」需求用的。放开时要同时改 `task.py`（属性 + setter）和 `taskSystem.py`（更新方法），只改一边会直接报 `AttributeError`。

## 四、索引与编号约定（最容易出错）

- `TaskSystem` 内部索引从 **0** 开始，用户看到的编号从 **1** 开始，菜单层必须做 `user_input - 1` 转换。
- **标记完成、删除一律使用「查看全部任务」的编号**；筛选、排序结果只用于查看，不能拿来当操作编号，避免认错任务。
- 删除使用 `list.pop(idx)` 会**让后面所有任务的索引前移**，因此任何时候都不要在菜单里缓存索引跨操作使用（例如先记下编号、让用户去别的菜单逛一圈再回来删）。这也是删除/完成必须现场重新读取编号的原因。

## 五、修改后的自检清单

- [ ] `Task` 新字段有没有默认值？有没有配套 `@property`（要能改的再加 setter 校验）？
- [ ] `__init__` 参数列表有没有被动过？`Task(title)` 还能正常调用吗？（硬性规定：一个字都不能改）
- [ ] 新字段是不是走「先创建默认值 → 再用 `update_xxx` 按流程设值」，而不是直接把值塞进构造函数？
- [ ] 菜单层有没有调用 `_get_by_index()` 或直接改 `Task` 的私有字段？
- [ ] 新增的修改方法是否返回 `bool`、是否先做越界判断？
- [ ] 改过的方法签名，是否排查了 `menus/` 下所有调用点？
- [ ] 数据格式（`|` 分隔、字段顺序、日期补 0）在存储/显示/解析三处是否一致？
- [ ] 用非法输入自测：空标题、超大编号、非数字、直接回车，程序不崩溃、不出现报错堆栈。
