# MyTodoProject 测试指南

本文档说明项目测试集的**结构、用法和扩展方式**，面向组内所有成员。

测试集的目的：改动代码后能**一条命令**确认没有把已有功能改坏，尤其是「输入健壮性」这类需求——靠手工点菜单很难覆盖全，用脚本跑几百种乱输入才靠谱。

---

## 一、快速开始

在**仓库根目录**执行：

```bash
python run_tests.py
```

看到结尾是 `全部通过 ✓` 就说明当前代码没问题。这就是全部——不需要装任何东西。

> 依赖：仅 Python 标准库（`unittest` + `subprocess`），无需 `pip install`。
> 若项目有 `.venv`，脚本会自动优先用它里面的 Python。

---

## 二、命令一览

| 命令 | 作用 |
| --- | --- |
| `python run_tests.py` | 运行**全部**测试（91 个用例） |
| `python run_tests.py -v` | 详细模式，逐条打印用例名与结果 |
| `python run_tests.py unit` | 只跑**白盒单测**（65 个） |
| `python run_tests.py brute` | 只跑**黑盒暴力测试**（26 个） |
| `python run_tests.py -k 关键字` | 只跑**用例名含关键字**的测试 |

`-k` 例：

```bash
python run_tests.py -k bom        # 只跑所有 BOM 相关的用例
python run_tests.py -k delete     # 只跑删除相关的用例
python run_tests.py -k empty_list # 只跑空清单相关用例
```

**退出码**：`0` = 全部通过，`1` = 有失败。方便接入 CI 或别的脚本。

## 三、测试集结构

```
MyTodoProject/
├── run_tests.py              # 全自动测试入口（唯一需要手动运行的文件）
└── tests/                    # 所有测试代码
    ├── __init__.py
    ├── helpers.py            # 公共工具：跑 main.py、数据隔离、菜单编号常量
    ├── test_task_model.py    # 白盒：Task 类
    ├── test_task_system.py   # 白盒：TaskSystem
    ├── test_persistence.py   # 白盒：taskSL 存取 / BOM / 损坏数据
    ├── test_menus.py         # 白盒：菜单系统与各菜单
    └── test_brute_force.py   # 黑盒：端到端暴力测试
```

### 白盒 vs 黑盒

| 类型 | 做法 | 好处 | 文件 |
| --- | --- | --- | --- |
| **白盒单测** | 直接 `import` 类/函数调用 | 快、能精确断言内部行为、能测边界值 | `test_task_*.py`、`test_menus.py`、`test_persistence.py` |
| **黑盒端到端** | `subprocess` 跑 `src/main.py`，喂模拟输入 | 最接近真实使用，验证整个程序不崩 | `test_brute_force.py` |

两者互补：白盒查「函数算得对不对」，黑盒查「程序整体会不会崩」。

## 四、各文件测试内容

### `test_task_model.py`（Task 类）
- 标题校验：空、纯空格、`None` 都要报错；正常标题自动去首尾空格
- 优先级：三档取值正确（高/中/低），写入非枚举值报错
- 截止日期：写入 `datetime` 会置 `has_due_date`；写入字符串/数字报错；`has_due_date` 只读
- 完成状态：只接受 `bool`，写 `1`/`"true"` 报错
- `to_string()`：四种组合的输出格式（含/无日期、已完成/未完成）

### `test_task_system.py`（TaskSystem）
- 增删、计数、`CreateFromList`（含空列表/`None`，且不别名外部列表）
- `get_by_index` / `get_all_tasks` 返回**内部引用**（已移除 deepcopy 保护）：读到的就是内部对象，改动会直接生效
- 越界索引返回 `None` / `False`
- `update_completed` / `update_priority` / `update_due_date` 正常与越界

### `test_persistence.py`（taskSL 存取）
- 保存自动建目录、写文件
- **保存→读取往返**数据一致
- 自写文件**不带 BOM**
- **读带 BOM 的文件**（记事本另存场景，回归用例）
- 损坏 JSON → 返回 `None`；单条记录损坏 → 跳过它保留其它
- 二次保存覆盖旧文件

> 该文件通过 `monkeypatch` 把数据路径指到临时目录，**不影响真实 `data/`**。

### `test_menus.py`（菜单）
- `MenuSystem`：注册分配连续编号、分发、非法编号返回 `-1`、空系统返回 `-1`
- **所有菜单空清单**都应返回 `0` 且**不索要输入**（用 `input` 抛断言来兜底）
- **所有菜单成功路径返回 `int 0`**（回归：曾隐式返回 `None`）
- 添加任务：正常/取消/空标题重问/坏日期跳过
- 关键字搜索的**关联度排序**：完全匹配 > 出现多次 > 词尾匹配 > 靠后出现；不匹配被过滤、大小写不敏感、空关键字返回全部、关键字含正则元字符按字面匹配
- 导出报告：生成 `report_*.html`、含统计与逾期样式

### `test_brute_force.py`（暴力端到端）

**核心断言**：无论输入什么，程序都**不得输出 `Traceback`**，且**退出码为 `0`**。

覆盖场景：

| 场景 | 举例 |
| --- | --- |
| 主菜单垃圾输入 | 字母、小数、负数、超大数、`0x10`、`1e9`、全角数字、emoji、命令注入样式、5000 长串、50 个空回车、立即 EOF |
| 添加任务 | 坏优先级、坏日期、空标题循环、含 `\|` 标题、超长标题 |
| 搜索筛选 | 6 种选项全走 + 非法选项 + 空/超长关键字 + 结果按关联度排序 + 正则元字符/全角空格/emoji 关键字 |
| 标记完成 / 删除 / 设置日期 / 设置优先级 | 全套边界值（`0`、`-1`、`999`、`abc`、空） |
| 删除二次确认 | `n`/`N`/`no`/`y`/`Y`/`yes`/空/乱写 |
| **数据文件损坏** | 13 种畸形 JSON（空串、`{}`、`[1,2,3]`、非法优先级、日期类型错、`null`…）+ BOM + 混合正常/损坏记录 |
| 持久化 | 保存→重启→读回；多次添加；统计与完成率 |
| 导出报告 | 默认目录 / 非法目录退回 |
| 混合长会话 | 添加→查看→筛选→标记→改优先级→改日期→删除→导出 |

## 五、数据隔离与自动清理（重要）

**问题**：程序的数据在 `data/tasks.json`，报告在 `reports/`。测试如果直接写这些真实路径，会**弄丢你正在用的数据**。

**解决**：

1. **黑盒测试**用 `DataSandbox`（在 [tests/helpers.py](../tests/helpers.py)）：
   - 开始前把真实 `data/` 备份到临时目录；
   - 测试期间随便写；
   - 结束后删掉测试产生的 `data/`，把备份恢复回去。

2. **脚本自动清理**：[run_tests.py](../run_tests.py) 在**运行前后各清理一次** `data/` 和 `reports/`，保证跑完工作区干净。

> 因此：**测试跑完 `git status` 不应该出现 `data/`、`reports/`**。如果出现了，说明有测试绕过了隔离，属于 bug，要修。

## 六、如何新增测试

### 加一个白盒用例
在对应文件里新建方法，名字以 `test_` 开头：

```python
class TestMyFeature(unittest.TestCase):
    def test_something(self):
        self.assertEqual(1 + 1, 2)
```

### 加一个黑盒用例
在 [tests/test_brute_force.py](../tests/test_brute_force.py) 里继承 `BruteBase`（它已自动帮你隔离数据）：

```python
class TestMyScenario(BruteBase):
    def test_my_input(self):
        proc = self.run_ok([MENU_ADD, "标题", "3", "2026-10-08", "", MENU_EXIT])
        self.assertIn("添加成功", proc.stdout)
```

- `self.run_ok(inputs)`：运行 main.py 并断言「无 Traceback + 退出码 0」，返回进程结果。
- 菜单编号用 [tests/helpers.py](../tests/helpers.py) 顶部的常量（`MENU_ADD` 等），**不要写死数字**——菜单顺序变了只需要改一处常量。

### 菜单顺序变了怎么办？
只改 [tests/helpers.py](../tests/helpers.py) 里那一组 `MENU_*` 常量即可。当前顺序：

```
1=查看全部  2=添加任务  3=搜索与筛选  4=删除任务
5=标记完成  6=设置截止日期  7=设置优先级  8=导出报告  0=退出
```

## 七、常见问题

**Q1：能装 pytest 吗？**
可以，但没必要。当前用标准库 `unittest`，`python run_tests.py` 即可，零依赖更好维护。想用 pytest 直接 `pytest tests/` 也能跑（用例是标准 `unittest.TestCase`）。

**Q2：测试太慢？**
主要慢在 25 个黑盒用例每次都要新起一个 Python 进程（约 20 多秒）。日常只改数据逻辑时跑 `python run_tests.py unit` 会快很多。

**Q3：看到 `[错误] 任务数据文件读取失败` 是不是测试挂了？**
不是。那是**故意喂损坏 JSON** 时 `main.py` 正常打印的错误日志，属于预期行为；判断通过与否只看结尾的 `全部通过 ✓` 和退出码。

**Q4：为什么断言「无 Traceback」而不是逐字比对输出？**
逐字比对太脆（改一句提示文案就红）。核心要求是「乱输入不崩溃」，所以黑盒断言「不抛异常 + 正常退出 + 关键信息出现」，稳定又好维护。

**Q5：测试会动我的接口签名吗？**
不会。测试只读/调用现有代码。若你改了 `TaskSystem` 的方法签名，相关用例会失败提醒你——这正是它的价值（[task与taskSystem修改注意事项.md](./task与taskSystem修改注意事项.md) 里提到接口要稳，测试就是守门员）。

## 八、提交规范

- 测试也是代码，同样走 PR 流程，提交类型用 `test`。
- 例：`test(tests): 补充删除任务的边界用例`
- 改动被测功能时，**同一个 PR 里补/改对应用例**，不要只改功能不补测试。
